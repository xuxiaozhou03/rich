# ETF 量化研究与回测系统 — 总体设计

- 文档版本：V0.1
- 文档状态：设计中
- 文档类型：系统级总体设计
- 目标读者：Codex、项目开发者
- 技术栈：TypeScript、Next.js、Prisma、SQLite

## 1. 项目概述

### 1.1 项目定位

构建一个面向 ETF 的量化研究与回测系统，覆盖数据管理、特征计算、ETF 研究分析、策略开发、投资组合管理、历史回测、策略评估和实盘信号等能力。

系统以 ETF 历史行情及相关基础数据为基础，将数据加工为标准化特征，通过研究分析和策略引擎构建投资策略，并通过回测引擎验证策略在历史市场环境中的表现。

系统不仅用于策略回测，也用于：

- ETF 历史表现分析。
- ETF 多维度比较和排名。
- ETF 特征及因子研究。
- 量化策略编写和验证。
- 多 ETF 投资组合构建。
- 历史交易模拟和绩效评估。
- 日常策略信号生成。

### 1.2 核心目标

1. 建立统一、可靠的 ETF 历史数据基础。
2. 建立可复用的 ETF 特征计算体系。
3. 支持 ETF 多维度分析、比较和排名。
4. 支持通过 TypeScript 代码编写量化策略。
5. 支持单 ETF 和多 ETF 组合回测。
6. 提供完整的交易、资金、持仓和收益核算。
7. 支持策略绩效分析和参数优化。
8. 为后续实盘信号生成提供统一的计算能力。

### 1.3 研究范围

当前系统以 A 股 ETF 为主要研究对象。

设计上允许未来扩展到其他市场 ETF，但 V1.0 优先保证现有 A 股 ETF 数据和业务流程完整。

当前不以股票个股交易、期货、期权、融资融券等作为首期实现范围。

## 2. 产品功能范围

系统围绕八个一级模块组织。

| 模块                      | 核心能力                         |
| ------------------------- | -------------------------------- |
| Data Management           | 数据采集、校验、存储、更新和读取 |
| Feature Engine            | ETF 日度特征计算                 |
| Research Engine           | ETF 分析、比较、排名和因子研究   |
| Strategy Engine           | 策略定义、策略执行和信号生成     |
| Portfolio Engine          | 组合构建、资金分配和仓位管理     |
| Backtest & Trading        | 历史回测、订单成交模拟和账户核算 |
| Evaluation & Optimization | 策略绩效评估、风险分析和参数优化 |
| Live Signal               | 基于最新数据生成策略信号         |

以上为系统逻辑模块，不要求每个模块都独立部署。首期采用单体应用内的模块化架构。

## 3. 整体系统架构

### 3.1 模块关系

主要业务链路：

Data Management
→ Feature Engine
→ Research Engine
→ Strategy Engine
→ Portfolio Engine
→ Backtest & Trading
→ Evaluation & Optimization
→ Live Signal

模块之间允许按职责进行必要的反向数据引用和结果反馈，不强制所有数据只能单向流动。

### 3.2 模块职责

#### 3.2.1 Data Management（数据管理）

负责系统基础数据的获取、管理和读取。

主要职责：

- ETF 基础信息管理。
- ETF 前复权日 K 线管理。
- ETF 最新规模和溢价率管理。
- ETF 最新持仓管理。
- ETF 关联关系管理。
- 指数历史估值管理。
- 指数最新行业权重管理。
- 数据采集、标准化、校验和更新。
- 向其他模块提供统一数据读取能力。

不负责量化指标计算、ETF 研究结论和策略信号生成。

详细设计见：`01-数据管理模块.md`。

#### 3.2.2 Feature Engine（特征计算引擎）

负责将原始数据转换为标准化量化特征。

包含七类特征：

- Market：行情特征。
- Performance：表现特征。
- Risk：风险特征。
- Technical：技术指标。
- Valuation：估值特征。
- Relative Strength：相对强度。
- Liquidity：流动性特征。

核心输出为 `EtfDailyFeatures`，代表一只 ETF 在一个日期的特征集合。

支持历史特征计算、每日增量计算和历史数据修正后的重新计算。

持仓和行业暴露（Exposure）不放入 `EtfDailyFeatures`，作为独立分析能力处理。

详细设计见：`02-特征计算引擎.md`。

#### 3.2.3 Research Engine（研究分析引擎）

负责基于基础数据和特征数据开展 ETF 研究。

主要职责：

- 单只 ETF 多维度分析。
- 多只 ETF 横向比较。
- ETF 分类分析。
- ETF 排名。
- 自定义分类权重和评分规则。
- ETF 因子研究。
- 特征有效性分析。
- 持仓和行业暴露分析。

研究分析模块负责解释和组织特征，不负责底层行情采集和基础指标计算。

详细设计见：`03-研究分析引擎.md`。

#### 3.2.4 Strategy Engine（策略引擎）

负责定义和执行量化策略。

主要职责：

- 策略定义和配置。
- 策略代码管理。
- 策略运行环境。
- 获取策略运行所需的历史数据和特征。
- 生成买入、卖出或持有等策略信号。
- 支持单 ETF 和多 ETF 策略。

策略采用 TypeScript 代码模式，具体执行隔离方式、策略接口和生命周期在专项文档中确定。

策略负责表达交易决策，不直接负责账户资金和成交核算。

详细设计见：`04-策略引擎.md`。

#### 3.2.5 Portfolio Engine（组合管理引擎）

负责将策略信号转换为组合层面的资金和仓位决策。

主要职责：

- ETF 候选范围管理。
- 组合资产配置。
- ETF 资金权重分配。
- 目标持仓计算。
- 仓位约束。
- 组合风险和暴露汇总。

组合管理负责决定组合持有什么、持有多少，不负责实际成交和账户记账。

详细设计见：`05-组合管理引擎.md`。

#### 3.2.6 Backtest & Trading（回测与交易引擎）

负责模拟历史交易过程并核算账户结果。

主要职责：

- 回测任务管理。
- 历史日期推进。
- 策略和组合调用。
- 订单生成及管理。
- 成交模拟。
- 手续费和交易规则处理。
- 资金、持仓和成本核算。
- 每日资产及收益记录。
- 交易明细和回测结果输出。

首期采用日 K 线收盘价模拟成交，具体成交时点、交易规则和边界处理由专项文档确定。

详细设计见：`06-回测与交易引擎.md`。

#### 3.2.7 Evaluation & Optimization（评估与优化）

负责评估策略和回测结果。

主要职责：

- 收益和风险绩效评估。
- 基准比较。
- 回撤和收益分布分析。
- 交易统计分析。
- 参数优化。
- 不同市场阶段的表现分析。
- 策略稳健性分析。

该模块消费回测结果，不负责重新模拟交易。

详细设计见：`07-评估与优化引擎.md`。

#### 3.2.8 Live Signal（实盘信号）

负责使用最新可用数据运行策略并生成信号。

主要职责：

- 获取最新行情和特征。
- 执行指定策略。
- 生成最新买卖信号。
- 记录信号和生成时间。
- 展示策略当前状态。

首期定位为信号研究和辅助决策，不直接接入券商自动下单。

详细设计见：`08-实盘信号模块.md`。

## 4. 核心数据设计

### 4.1 当前已有数据模型

系统使用 Prisma + SQLite。

当前已有六个核心数据模型：

| 模型      | 数据内容                         | 数据性质           |
| --------- | -------------------------------- | ------------------ |
| Etf       | ETF 基础信息、分类、规模、溢价率 | 基础信息及最新快照 |
| Kline     | ETF 日 K 线                      | 前复权历史行情     |
| Link      | ETF 关联关系                     | 最新关系           |
| Holding   | ETF 成分持仓                     | 最新一期快照       |
| Valuation | 指数 PE/PB/PS 等估值             | 历史时间序列       |
| Sw        | 指数申万行业权重                 | 最新快照           |

以上六个模型是当前数据管理模块的基础，不在系统总纲阶段擅自增加数据表。

具体字段和数据更新规则以数据管理模块文档为准。

### 4.2 当前数据模型定义

```prisma
model Etf {
  code        String  @id
  name        String
  indexCode   String
  indexName   String?
  premiumRate Float?
  category    String
  scale       Float

  @@map("etfs")
}

model Link {
  target  String
  source  String
  similar Float?

  @@id([target, source])
  @@map("links")
}

model Holding {
  code      String
  stockCode String
  stockName String
  holdScale Float

  @@id([code, stockCode])
  @@map("holdings")
}

model Kline {
  code          String
  date          Int
  open          Float
  high          Float
  low           Float
  close         Float
  volume        Float
  amount        Float
  change        Float
  changePercent Float

  @@id([code, date])
  @@map("klines")
}

model Valuation {
  indexCode String
  type      String
  date      Int
  value     Float
  percent   Float?
  peg       Float?

  @@id([indexCode, type, date])
  @@index([indexCode, type, date])
  @@map("valuations")
}

model Sw {
  indexCode    String
  level        Int
  industryCode String
  industryName String
  weight       Float

  @@id([indexCode, level, industryCode])
  @@index([indexCode, level, weight])
  @@map("sws")
}
```

### 4.3 数据范围约束

当前版本：

- 不采集指数行情。
- 不采集股票基础信息和股票行情。
- 不保存 ETF 历史规模。
- 不保存 ETF 历史溢价率。
- 不保存历史持仓快照。
- 不保存历史行业权重快照。
- 不增加独立交易日历模型。
- 不增加 ETF 交易状态模型。
- 不增加 ETF 研究池模型。

ETF 分类使用 `Etf.category`。

ETF 实际有行情的日期以 `Kline` 为依据。多 ETF 组合回测需要基于参与 ETF 的有效行情日期进行统一日期推进。

## 5. 核心数据口径

### 5.1 价格口径

系统所有历史价格分析统一采用前复权（QFQ）行情。

包括：

- 历史收益率。
- 波动率和回撤。
- 技术指标。
- 特征计算。
- 策略信号。
- 回测价格模拟。
- 持仓市值和收益分析。

当前 `Kline` 表只保存前复权数据，不存在独立的原始行情表。

### 5.2 回测价格说明

首期采用日 K 线收盘价模拟成交。

由于前复权价格并非历史真实成交价格，基于前复权价格得到的回测成交结果属于研究模拟结果，不代表真实历史可成交价格。

系统需要在回测结果中明确这一假设。

未来如果接入实盘交易，必须使用实际市场价格和真实成交记录，不得将前复权价格当作实盘成交价格。

### 5.3 时间与数据可用性

所有历史计算必须遵循数据可用时间约束。

- 计算某日特征时，只能使用该日期及之前的数据。
- 历史策略决策不得使用未来行情和未来估值。
- 最新规模、溢价率、持仓和行业权重只能代表最新快照。
- 不得将最新快照直接回填到历史日期。
- 回测中必须明确策略信号生成时间和模拟成交时间。

### 5.4 数据缺失

没有有效行情的日期不能被当作正常成交日。

对于某 ETF 某日缺少 K 线的情况，应由相关模块根据业务规则处理，不得随意使用未来数据补齐。

## 6. 核心业务流程

### 6.1 数据准备流程

1. 采集 ETF 基础信息及相关数据。
2. 采集并更新 ETF 前复权日 K 线。
3. 更新指数估值。
4. 更新最新持仓、行业权重、规模和溢价率。
5. 执行数据校验。
6. 数据通过校验后提供给计算模块。

### 6.2 特征计算流程

1. 获取指定 ETF 的历史 K 线及相关估值。
2. 执行特征计算。
3. 生成 `EtfDailyFeatures`。
4. 保存计算结果。
5. 支持历史数据修正后重新计算。

### 6.3 研究分析流程

1. 读取 ETF 基础信息和特征。
2. 计算单 ETF 分析结果。
3. 计算多 ETF 比较和排名。
4. 根据需要开展因子研究。
5. 输出研究结果。

### 6.4 策略回测流程

1. 创建回测任务。
2. 指定策略、ETF 范围、回测时间和初始资金。
3. 回测引擎按历史日期推进。
4. 获取当日可用行情和特征。
5. 执行策略，生成交易信号。
6. 组合管理模块计算目标仓位和资金分配。
7. 回测引擎生成订单并模拟成交。
8. 更新账户资金、持仓和成本。
9. 记录每日资产、交易明细和收益。
10. 生成回测结果。
11. 评估模块分析回测绩效。

## 7. 核心系统设计原则

### 7.1 模块职责单一

每个模块只负责自身业务，不跨模块承担其他职责。

模块间通过明确的输入、输出和接口协作。

### 7.2 数据与计算分离

原始数据由 Data Management 管理。

量化特征由 Feature Engine 计算。

研究结论由 Research Engine 组织。

策略决策由 Strategy Engine 生成。

资金和持仓由 Portfolio Engine 管理。

成交和账户核算由 Backtest & Trading 管理。

### 7.3 计算可复现

相同的数据、参数、策略版本和计算规则，应产生一致的计算结果。

回测结果需要能够追溯：

- 使用的数据范围。
- 策略版本。
- 策略参数。
- 回测配置。
- 交易规则。
- 计算结果。

### 7.4 防止未来数据泄漏

历史特征、策略信号和回测决策必须严格遵循当时可用的数据。

任何模块都不能在历史计算中无意使用未来信息。

### 7.5 统一类型规范

系统采用 TypeScript。

跨模块数据通过明确的 TypeScript 类型定义，不使用缺少约束的随意对象传递业务数据。

### 7.6 先保证正确性，再考虑性能

首期优先保证：

- 计算口径正确。
- 数据时间正确。
- 模块边界清晰。
- 结果可复现。
- 测试可验证。

在数据规模和性能确实成为瓶颈后，再考虑并行计算、缓存和其他优化。

## 8. 技术架构

### 8.1 技术栈

| 技术            | 用途                   |
| --------------- | ---------------------- |
| TypeScript      | 核心业务和计算逻辑     |
| Next.js         | Web 应用和服务端能力   |
| Prisma          | 数据访问和 ORM         |
| SQLite          | 首期数据库             |
| trading-signals | 技术指标计算，按需引入 |

技术指标优先复用 `trading-signals` 等成熟 TypeScript 库，不重复实现已有且经过验证的基础指标。

第三方库仅作为计算工具，业务指标的参数、输入口径和输出定义由本系统控制。

### 8.2 应用架构

首期采用模块化单体架构。

- 不拆分微服务。
- 不引入独立消息队列。
- 不要求每个引擎独立部署。
- 各模块保持清晰的目录、类型和接口边界。
- 核心计算逻辑尽量与 Web 页面和数据库访问解耦。

### 8.3 数据访问

业务模块原则上通过统一的数据读取接口访问持久化数据，不在各个模块中随意散布 Prisma 查询。

具体 Repository / Data Provider 接口在数据管理模块专项文档中定义。

## 10. 开发实施规划

采用分阶段开发，先打通基础链路，再逐步完善研究和策略能力。

### 阶段一：数据与特征基础

- 数据管理模块。
- 特征计算引擎。
- 数据读取接口。
- 全量和增量特征计算。

### 阶段二：ETF 研究分析

- 单 ETF 分析。
- ETF 比较。
- ETF 分类和排名。
- 因子研究。
- 持仓和行业暴露分析。

### 阶段三：策略与组合

- 策略接口。
- TypeScript 策略执行。
- 策略配置。
- 组合构建。
- 资金分配和仓位约束。

### 阶段四：回测与评估

- 回测任务管理。
- 历史日期推进。
- 订单和成交模拟。
- 账户和持仓核算。
- 回测结果记录。
- 绩效评估。

### 阶段五：优化与实盘信号

- 参数优化。
- 策略稳健性分析。
- 最新行情和特征更新。
- 策略信号生成。
- 信号记录和展示。

各阶段的详细任务、依赖和验收标准在 `09-开发实施计划.md` 中定义。

## 13. 总纲维护规则

本文件是系统级设计的唯一总纲入口。

后续设计和开发遵循：

1. 新增模块能力时，先明确所属模块。
2. 具体业务规则在对应专项文档中定义。
3. 模块间职责发生变化时，同步更新本总纲。
4. 已确认的设计决策不能在实现过程中被 Codex 擅自改变。
5. 如发现设计存在冲突或无法实现，应先指出问题，不得自行扩大系统范围。
6. 总纲持续维护版本，重大架构变化记录变更原因。

当前 V0.1 主要用于确定系统整体方向。待各模块专项设计完成并完成一致性检查后，升级为系统总体设计 V1.0。

接下来明确 **9 个模块之间的输入、输出和数据流**。

这里有一个重要原则：不能简单地把 9 个模块串成一条流水线。因为研究、策略、回测是不同的工作流，它们会复用数据和计算结果，但不应该相互耦合。

我建议把系统分成三条主要工作流：

1. **数据与特征工作流**：采集数据，验证数据，计算特征。
2. **研究工作流**：利用历史数据和特征，研究 ETF、因子和投资逻辑。
3. **策略与回测工作流**：运行策略、生成组合、模拟交易、评价结果。

## **一、9 个模块的输入与输出**

### **01. Data Management — 数据管理**

职责：负责外部数据进入系统，以及数据质量和持久化。

| 输入         | 输出               |
| ------------ | ------------------ |
| 外部数据源   | ETF 基础信息       |
| 采集配置     | 前复权日 K 行情    |
| 采集任务     | 最新规模、溢价率   |
| 数据验证规则 | 最新持仓、行业权重 |
| 数据修订信息 | 数据质量与采集记录 |

内部流程：

`数据采集 → 数据验证 → 数据存储`

注意：数据验证不通过的数据不能直接进入正式数据集；需要保留异常记录，支持后续修复和重新验证。

### **02. Feature Engine — 特征引擎**

职责：把原始行情和 ETF 数据转换为可复用的量化特征。

| 输入               | 输出                 |
| ------------------ | -------------------- |
| 前复权日 K         | Market Features      |
| ETF 基础信息       | Performance Features |
| 最新规模、溢价率   | Risk Features        |
| 最新持仓、行业权重 | Technical Features   |
| 特征计算配置       | Valuation Features   |
| 计算日期、历史行情 | Relative Features    |
|                    | Labels               |

主要产物：

- 单 ETF 每日特征。
- 多 ETF 横截面特征，例如 RPS、排名。
- 未来收益标签。
- 市场状态标签。

这里要特别注意：未来收益标签只能用于历史研究和训练分析，不能作为当日策略的可用输入。

### **03. Analyze Engine — 分析引擎**

职责：基于行情和特征，研究 ETF 表现、因子有效性和市场规律。

| 输入                | 输出               |
| ------------------- | ------------------ |
| ETF 行情和基础数据  | 单 ETF 分析报告    |
| Feature Engine 结果 | ETF 横向比较       |
| ETF Universe        | 因子 IC / Rank IC  |
| 研究配置            | 分组收益分析       |
| 历史区间            | 因子衰减与稳定性   |
|                     | 市场规律和研究结论 |

例如：

- 哪些 ETF 在过去一年表现更好？
- RPS 是否对未来收益有预测能力？
- 哪些技术指标在什么市场环境下更有效？
- 高成交额 ETF 是否具有更好的流动性？

### **04. Strategy Engine — 策略引擎**

职责：根据策略逻辑和当时可用的信息，产生交易决策。

| 输入                | 输出                 |
| ------------------- | -------------------- |
| TypeScript 策略代码 | 买入、卖出、持有意图 |
| 策略参数            | ETF 选择结果         |
| ETF Universe        | 策略运行状态         |
| 当日可用特征        | 调仓意图             |
| 当前持仓和账户状态  | 策略日志             |

策略不直接执行交易，也不直接修改账户资金和持仓。

### **05. Portfolio Engine — 组合管理引擎**

职责：将策略决策转换为目标投资组合。

| 输入           | 输出                   |
| -------------- | ---------------------- |
| 策略选股结果   | 目标 ETF 持仓          |
| 当前资金和持仓 | 目标权重               |
| 组合配置规则   | 目标金额和数量         |
| 风险控制配置   | 调仓计划               |
| 交易约束       | 组合风险与约束检查结果 |

例如：

策略选出 ETF A、B、C，组合管理根据配置规则生成 50%、30%、20% 的目标权重，再结合当前持仓计算需要调整的数量。

### **06. Backtest Engine — 回测引擎**

职责：在历史行情中模拟交易，维护账户状态。

| 输入             | 输出         |
| ---------------- | ------------ |
| 策略版本与参数   | 订单记录     |
| 历史行情         | 成交记录     |
| 组合调仓计划     | 账户资金变化 |
| 初始资金         | 持仓变化     |
| 手续费、滑点规则 | 每日净值     |
| ETF 交易规则     | 回测运行日志 |

它负责模拟真实交易过程，但不连接券商、不执行实盘订单。

### **07. Evaluation Engine — 评价引擎**

职责：评价研究结果和回测策略的表现。

| 输入           | 输出       |
| -------------- | ---------- |
| 回测结果       | 收益分析   |
| 每日净值       | 风险分析   |
| 订单与成交记录 | 交易分析   |
| 持仓记录       | 基准对比   |
| 评价配置       | 稳健性分析 |

### **08. Experiment Management — 实验管理**

职责：管理研究和回测的完整实验过程，保证结果可追溯、可比较、可复现。

| 输入     | 输出             |
| -------- | ---------------- |
| 研究任务 | 研究实验记录     |
| 策略版本 | 回测实验记录     |
| 策略参数 | 实验对比         |
| 数据版本 | 实验历史         |
| 特征版本 | 可复现的实验配置 |
| 运行结果 | 实验报告关联     |

它不是计算引擎，而是管理实验生命周期的模块。

### **09. Application — 应用层**

职责：为用户提供统一的 Web 操作入口。

| 输入           | 输出               |
| -------------- | ------------------ |
| 用户操作       | 数据管理界面       |
| 各模块服务结果 | ETF 分析界面       |
| 研究和回测结果 | 策略编辑与回测界面 |
| 任务状态       | 组合与绩效展示     |
| 实验记录       | 实验管理界面       |

Application 不直接实现特征计算、研究分析或回测逻辑。

## **二、模块之间的整体数据流**

这部分最关键的是明确：**谁生产数据、谁消费数据、谁负责驱动整个流程。**

我建议采用下面的关系。

**Data Management**

ETF 基础信息 · 前复权日 K · 最新规模/溢价率/持仓

**Feature Engine**

单 ETF 特征 · 横截面特征 · 未来收益标签

**Analyze Engine**

研究分析

**Strategy Engine**

策略决策

研究和策略都消费特征，但两者没有直接依赖关系

**Portfolio Engine**

目标持仓 · 目标权重 · 调仓计划

**Backtest Engine**

订单 · 成交 · 资金 · 持仓 · 净值

**Evaluation Engine**

收益 · 风险 · 交易 · 基准 · 稳健性

**Experiment Management**

关联研究、策略、数据、特征版本和执行结果

**Application**

统一操作入口，调用各模块服务

这个图表达的是主要数据依赖，不代表所有模块都只能按这个顺序执行。

例如 Analyze Engine 的研究结果可以帮助用户设计策略，但 Strategy Engine 不应该在运行时依赖某一份研究报告才能工作。

## **三、策略与回测的数据流需要特别明确**

这是整个系统最重要的一条执行链路。

假设我们要做一个每 5 个交易日进行一次 ETF 轮动的策略：

1. **Backtest Engine 推进交易日**

   推进到某个交易日，提供当日允许使用的行情、特征和账户状态。

2. **Strategy Engine 产生决策**

   根据 RPS、收益率、风险等特征，选出需要持有的 ETF。

   输出：ETF A、ETF B、ETF C。

3. **Portfolio Engine 计算目标组合**

   根据资金、持仓、权重规则和风险约束，计算目标配置。

   输出：A 50%、B 30%、C 20%。

4. **Backtest Engine 模拟交易**

   根据目标组合生成订单，按照成交规则、手续费和滑点模拟成交。

5. **Backtest Engine 更新账户**

   更新现金、持仓、成本、每日净值和交易记录。

6. **Evaluation Engine 评价结果**

   计算收益率、年化收益、最大回撤、夏普比率、胜率等指标。

7. **Experiment Management 保存实验**

   记录策略版本、参数、数据版本、运行配置和回测结果。

这里有一个架构细节：**Backtest Engine 应该是整个回测流程的执行调度者。**

它负责推进历史时间，并在每个策略决策时点依次调用 Strategy Engine 和 Portfolio Engine，再执行订单和更新账户。Strategy 和 Portfolio 不应该自己读取历史行情并模拟账户。

## **四、需要明确的四个关键边界**

### **1. Feature Engine 和 Analyze Engine**

两者都可能产生统计数据，但产物性质不同。

| 对比               | Feature Engine | Analyze Engine                 |
| ------------------ | -------------- | ------------------------------ |
| 目标               | 生产标准化特征 | 发现规律、验证假设             |
| 计算范围           | 单 ETF、跨 ETF | 单 ETF、跨 ETF、历史区间       |
| 计算结果           | 结构化特征数据 | 研究指标、分析报告             |
| 是否被策略直接使用 | 是             | 通常不直接使用                 |
| 示例               | RPS60 = 85     | RPS60 对未来收益是否有预测能力 |

例如：

- RPS60 = 85：Feature Engine。
- RPS60 与未来 20 日收益的相关性：Analyze Engine。
- RPS60 大于 80 时买入：Strategy Engine。

### **2. Strategy Engine 和 Portfolio Engine**

两者分别负责决策和配置。

| 对比     | Strategy Engine              | Portfolio Engine             |
| -------- | ---------------------------- | ---------------------------- |
| 核心问题 | 买什么、卖什么               | 买多少、持有多少             |
| 输入     | 特征、策略参数、当前组合状态 | 策略意图、账户状态、配置规则 |
| 输出     | 交易意图、目标标的           | 目标权重、目标持仓、调仓计划 |

例如：

- 策略决定持有排名前 3 的 ETF。
- 组合管理决定等权配置，还是按波动率分配。
- 回测引擎负责真正模拟交易。

### **3. Backtest Engine 和 Evaluation Engine**

| 对比     | Backtest Engine            | Evaluation Engine    |
| -------- | -------------------------- | -------------------- |
| 核心问题 | 历史上交易会怎样发生       | 交易结果好不好       |
| 输入     | 行情、策略、组合、交易规则 | 回测结果             |
| 输出     | 订单、成交、持仓、净值     | 收益、风险、交易评价 |

回测引擎不负责判断策略是否优秀，评价引擎也不负责重新模拟交易。

### **4. Experiment Management 不参与计算**

它更像一个实验管理中心。

例如，一次回测需要关联：

- 策略代码版本。
- 策略参数。
- ETF Universe。
- 行情数据版本。
- 特征计算版本。
- 回测区间。
- 初始资金。
- 手续费和滑点配置。
- 回测结果。

这样才能保证同一实验可追溯、可比较、可复现。

## **五、还需要注意一个数据时间问题**

这点对你的系统尤其重要。

你当前的数据范围中，有些数据只保存最新值，例如：

- 最新基金规模。
- 最新溢价率。
- 最新一期持仓。
- 最新行业权重。

这些数据可以用于当前 ETF 分析，但不能直接当成历史每天都已知的数据。

例如，2026 年 11 月获得的最新持仓，不能拿来模拟 2025 年的 ETF 轮动策略。

因此需要区分：

| 数据类型             | 使用方式                           |
| -------------------- | ---------------------------------- |
| 历史前复权日 K       | 可以用于历史特征和回测             |
| 最新规模、溢价率     | 当前分析使用                       |
| 最新持仓、行业权重   | 当前分析使用                       |
| 带历史有效时间的数据 | 满足时间约束后可用于历史研究和回测 |

这意味着：**系统必须具备数据可用时间（Available At）的概念，而不仅仅是数据所属日期。**

## **六、建议确认的最终模块边界**

到目前为止，我建议将模块职责固定为：

| 模块                  | 负责什么             | 不负责什么         |
| --------------------- | -------------------- | ------------------ |
| Data Management       | 获取、验证、存储数据 | 量化指标计算       |
| Feature Engine        | 生产量化特征         | 因子有效性研究     |
| Analyze Engine        | ETF 分析、因子研究   | 策略执行、交易模拟 |
| Strategy Engine       | 产生交易决策         | 资金和持仓实际变更 |
| Portfolio Engine      | 目标持仓和资金配置   | 订单撮合           |
| Backtest Engine       | 历史交易模拟         | 策略优劣评价       |
| Evaluation Engine     | 绩效和稳健性评价     | 交易模拟           |
| Experiment Management | 实验管理和结果追溯   | 业务计算           |
| Application           | 用户交互和展示       | 核心业务逻辑       |

**还有一个实现层面的建议：** 这 9 个模块是逻辑模块，不意味着必须拆成 9 个独立服务。第一版建议采用 TypeScript 模块化单体，模块之间通过明确的类型和服务接口协作。

## **七、下一步：确认系统的核心运行模式**

在进入数据库设计之前，我认为还有一个重要问题需要确认：系统究竟以什么方式组织研究和回测任务。

我建议采用三种独立运行模式：

1. **日常计算模式**：爬取数据 → 验证 → 存储 → 增量计算特征。
2. **研究分析模式**：选择 ETF 范围和历史区间 → 计算或读取特征 → 运行研究任务 → 保存研究结果。
3. **策略回测模式**：选择策略和参数 → 历史时间推进 → 策略决策 → 组合配置 → 模拟交易 → 结果评价。

三种模式共用 Data Management 和 Feature Engine，但各自有独立的任务生命周期。

我建议先按这三种模式作为系统的运行方式，接下来再明确每种模式的执行流程、任务状态和结果产物。
